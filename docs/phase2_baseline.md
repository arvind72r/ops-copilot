# Phase 2 — Baseline Agent
## Rules-Based Incident Triage: Design & Evaluation

**Agent:** OpsPilot | **Approach:** Deterministic rules (no LLM) | **Dataset:** 500 synthetic incidents

---

## Purpose

Phase 2 establishes a **non-LLM performance baseline** for OpsPilot.
Before adding an LLM, we measure how far pure rule-based logic can take us.
Every subsequent phase is compared against this baseline.

The baseline answers three operational questions:
1. How many incidents has a service had, and how severe?
2. Is a service's SLA breach rate within tolerance?
3. What is the overall health of the fleet right now?

---

## Synthetic Dataset

Generated by `data/generate_data.py` using `random.seed(42)` for reproducibility.

| Parameter | Value |
|-----------|-------|
| Total incidents | 500 |
| Date range | 2025-01-01 → 2026-05-28 |
| Services | 10 (auth-service, payments-api, database-cluster, api-gateway, …) |
| Severity distribution | P1 8%, P2 22%, P3 45%, P4 25% |
| SLA breach rate | ~30% overall (varies by service) |

### CSV Schema (`incidents.csv`)

| Column | Type | Notes |
|--------|------|-------|
| `incident_id` | str | INC-NNNN |
| `service` | str | one of 10 known services |
| `severity` | str | P1 / P2 / P3 / P4 |
| `status` | str | Open / In Progress / Resolved |
| `opened_at` | datetime | UTC timestamp |
| `resolved_at` | datetime | UTC or NaT if unresolved |
| `mttr_minutes` | float | Minutes to resolve; NaN if unresolved |
| `sla_breached` | str | "Yes" / "No" |
| `description` | str | Free-text incident summary |

## Baseline Agent Design

The baseline agent (`agent/baseline.py`) is a pure Python function — no LLM, no embeddings.
It accepts a structured query dict and applies Pandas filters + rule logic.

```
query dict  →  filter incidents by service / severity / time window
            →  compute counts, MTTR, breach rate
            →  apply health classification rule
            →  return plain-text summary string
```

### Health Classification Rules

| Condition | Status |
|-----------|--------|
| 0 open incidents AND breach rate < 20% | HEALTHY |
| ≤ 2 open incidents AND breach rate < 40% | DEGRADED |
| Otherwise | CRITICAL |

These thresholds were chosen to reflect realistic NOC escalation criteria.

### SLA Targets (`sla_targets.csv`)

Each service has a target SLA breach rate (e.g. "auth-service must stay below 15%").
The baseline agent compares actual vs target and flags when the target is exceeded.

## Evaluation Results

### Query Coverage

| Query Type | Baseline Handles? | Notes |
|-----------|-------------------|-------|
| Incident count by service / severity / days | ✅ | Pandas filter + count |
| MTTR average | ✅ | Mean of `mttr_minutes` / 60 |
| SLA breach rate | ✅ | `sla_breached == "Yes"` ratio |
| Service health snapshot | ✅ | Rule-based classification |
| Multi-service comparison | ⚠️ Partial | Must call twice, no synthesis |
| Natural language ("tell me about auth") | ❌ | Requires exact field match |
| Follow-up / pronoun resolution ("its SLA?") | ❌ | Stateless, no context |
| Runbook / escalation guidance | ❌ | No knowledge base |
| Trend analysis ("getting worse?") | ❌ | No temporal reasoning |

### Accuracy on Test Queries

| Query | Baseline Result | Correct? |
|-------|----------------|---------|
| P1 count for auth-service, last 30 days | Numeric count | ✅ |
| SLA breach rate for payments-api | Percentage | ✅ |
| Is database-cluster healthy? | HEALTHY/DEGRADED/CRITICAL | ✅ |
| "What should I do about the outage?" | ❌ Not answered | Expected — no LLM |
| "Compare auth-service and payments-api" | ❌ No synthesis | Expected — no LLM |

**Structured fact retrieval: ~100%**  
**Natural language understanding: 0%** (by design — baseline is rule-only)

## Baseline Limitations (Establish for Phase 3+)

| ID | Limitation | Impact | Fixed in |
|----|-----------|--------|---------|
| BL1 | No natural language understanding | Must pass structured dicts, not text | Phase 3 |
| BL2 | No contextual reasoning | Cannot answer "why" or "what should I do" | Phase 3 |
| BL3 | No knowledge retrieval | Runbooks, escalation steps not accessible | Phase 4 |
| BL4 | Stateless | No memory of prior queries in session | Phase 6 |
| BL5 | Single-service per call | Comparison requires 2 calls + manual merge | Phase 5 |
